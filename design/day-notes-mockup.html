The idea splits in two, and that decides everything

Some holidays are a rule — computable forever, never wrong, never stale. Others are a table — someone published dates, and the table runs out. A pack that mixes them silently without saying which is which is a pack that quietly goes wrong in 2029.

KindExamplesCan we compute it?
Fixed date Christmas · New Year · Independence Day · Valentine's ✓ Works today. yearly { month, monthDay } — the window we shipped this session.
Ordinal weekday Thanksgiving (4th Thu Nov) · Labor Day (1st Mon Sep) · MLK (3rd Mon Jan) · Memorial (last Mon May) ⚠ Small extension. We already compute "the 4th Thursday" for monthly patterns; yearly just needs to accept { month, nth, day } too. Then most US federal holidays are rules that never expire.
Computed Easter — and Ash Wednesday, Good Friday, Pentecost, which are all offsets from it ⚠ ~20 lines. The computus is a known, deterministic algorithm. One function unlocks the whole moveable set.
Another calendar Rosh Hashanah, Yom Kippur, Passover · Ramadan, Eid ✗ Do not hand-roll. Hebrew and Islamic calendars are lunisolar. Getting these subtly wrong is worse than not shipping them — these are people's religious observances. Either a dated table with a visible expiry, or import a published .ics.
Institutional BC's fall break, reading period, commencement ✗ No algorithm exists. The registrar decides each year. A bundled "BC" code is a table that rots every August — and BC publishes an academic calendar you can just import.

So the recommendation: ship packs, but make each one declare which it is. A rule pack is permanent and silent. A table pack shows the years it covers, so it can tell you it has run out instead of just being wrong.

And for BC specifically — that's an import, not a code. A code that needs re-publishing every August is a promise the app can't keep.

The year is optional — and that is how you say "every year"

Write 2027-05-24 and it happens once, in 2027. Drop the year — 09-03 — and it happens every year. No "repeats" toggle for the common case, because the way people already write a birthday says it: a birthday has a month and a day, and no year.

The one that needs a decision: a year-less range. "Every year, 9–13 March" is expressible, but our yearly window is a single day — a range would need five windows, or a new "spans N days" field on the note. Worth asking whether anyone actually wants a recurring multi-day note, given breaks move every year anyway (which is exactly why BC's calendar is an import, not a rule).

What a code actually is

A code is just a named set. A rule entry is a recurrence — the same shape a repeating task uses, so it reuses everything, including the skip rules (29 February appears only in leap years, no new code). A dated entry is a plain from/to, and the pack carries the years it covers so the card can warn you.
