## CONFIRMED

Ranked by how much the user would notice.

### 1. B110 — "Lay out this week" over-books a partly-done commitment and reports no shortfall

**Defect.** `layOutWeek` sends the engine `amountMin = remainingMin` but leaves
`minSitting` at `effectiveMinSitting()` of the **full** weekly amount, so a commitment
with a remainder smaller than its minimum sitting gets a block bigger than the work,
with `shortfall: 0` — breaking `placed + shortfall === amount` in the direction nobody
tests.

**File:line.**
- `src/core/commitmentWeek.js:134–139` — `layOutWeek` maps `{ ...p.input, amountMin: p.remainingMin }`; `p.input.minSitting` came from `Commitment#engineInputForWeek` (`src/core/Commitment.js:225`) and is `effectiveMinSitting()` = `min(minSitting, amountMinPerWeek)` — clamped against the **week's amount**, never against the **remainder**.
- `src/core/generate.js:165–167` — the single-sitting branch: `Math.min(Math.max(amountMin, sMin), only.minutes, sMax)` then `shortfall: Math.max(0, amountMin - minutes)`.

**Probe output (wrong value).**

```
B110b placedMin = 100 remainingMin = 20 state = owes
B110b engine input: amountMin(remaining) = 20 minSitting sent = 30 (effectiveMinSitting of the FULL amount = 30 )
B110b NEW sittings = [30] shortfall = 0 | asked for 20 got 30
B110b after lay-out: placedMin = 130 owedMin = 120 remainingMin = 0 over-book = 10
```

and the bare engine, same shape:

```
B110a placed = [30] shortfall = 0 | placed+shortfall = 30 vs amount 20
```

**Right value.** Either `[20] shortfall 0` (the `minSitting` floor yields to a smaller
amount, which is what `effectiveMinSitting()` exists to express) or `[] shortfall 20`.
The ledger must not end at `placedMin 130 / owedMin 120`.

**Anti-vacuity check.** The fixture reaches the arithmetic, not a stub: `previewWeek`
printed `placedMin = 100` before the lay-out, so the 100-minute pre-placed task really
was counted by the ledger; `state = owes` means the row passed `layOutWeek`'s
`state === 'owes' && remainingMin > 0 && input` filter rather than being skipped; and the
run printed the exact `minSitting` (30) that reached the engine next to the amount (20),
so the mismatch is the named mechanism and not a side effect of the gap layout. Under
correct behaviour the last line would have read `over-book = 0`. The bare `chooseSittings`
call is an independent second witness on the same branch with no schedule in the picture.

**Probe source** (`tests/zz-hunt2-commit.test.js`, abridged to the relevant test):

```js

  title: 'Duolingo', tags: ['study'],
  amountMinPerWeek: 120, from: '2026-09-07', until: '2026-12-11',

}));
const t = new Task({ title: 'Duolingo', tags: ['study'], type: 'flexible', parentId: c.id,
  startTime: at(0, 9), endTime: at(0, 10, 40) });   // 100 minutes, already done
t.completion = 'done';
s.tasks.push(t);
const row = previewWeek(s, MON, NOW).find((p) => p.commitment.id === c.id);
console.log('B110b placedMin =', row.placedMin, 'remainingMin =', row.remainingMin, 'state =', row.state);
console.log('B110b engine input: amountMin(remaining) =', row.remainingMin,
  'minSitting sent =', row.input.minSitting, '(effectiveMinSitting of the FULL amount =', c.effectiveMinSitting(), ')');

  '| asked for', row.remainingMin, 'got', mins.reduce((a, b) => a + b, 0));
```

**The case's own account of the risk is wrong in one respect and right in the
conclusion.** It says the bug is "saved today by exactly one thing:
`effectiveMinSitting()`", and that only a hand-built engine input reopens it. In fact
`effectiveMinSitting()` guards only the case where the *whole week's* amount is below
`minSitting`. The moment any minutes are already on the grid, `layOutWeek` — the real
button — walks straight into the branch. The clamp is computed against a number the
engine is no longer being given.

**Side finding, same function (low user visibility): the fold-back branch is dead code.**
`src/core/generate.js:154–162`. `room = Math.min(prev.gap ? prev.gap.minutes : prev.minutes, sMax) - prev.minutes`, but `prev` here is a **gap** object (from `usable`), which has no `.gap` property, and `usable` already capped `minutes` at `sMax` — so `room` is identically `0` and `room >= tail && tail > 0` can never hold. Four configurations chosen to land in that branch all fell through to the single-sitting or shortfall paths:

```
B110c amount=70 sMin=30 sMax=60 -> [60] shortfall = 10 | placed+shortfall = 70
B110c amount=70 sMin=30 sMax=120 -> [60] shortfall = 10 | placed+shortfall = 70
B110c amount=100 sMin=45 sMax=90 -> [60] shortfall = 40 | placed+shortfall = 100
B110c amount=65 sMin=60 sMax=90 -> [60] shortfall = 5 | placed+shortfall = 65
```

Conservation holds in every one of those, so the dead lever costs the user nothing today
— it is unexercised code, not a live defect. Recorded because the case is right that "a
conservation lever that has never once fired is indistinguishable from one that works".

### 2. B107 — the cross-validator's fold models are muzzled by the same cold-start threshold they are being tested against

**Defect.** `_assessSkill` fits a throwaway `LearningModule` per fold and asks it for a
`modelScore`; `modelScore` returns a hard `0` when `sampleCount < coldStartRatings`. For
a user with 12–14 ratings the fold training set falls below 10, every held-out prediction
is `0` against a truth of ~0.85, and `skill` comes out **catastrophically** negative — so
the gate silences the model in all four surfaces and the Cabana tells the user, in the one
place they came to look at the model, that "the fit does no better than guessing".

**File:line.**
- `src/core/learning.js:400–404` — `sub.train(train, { assessSkill: false })` then `pred = sub.trained ? sub.modelScore(t, null) : mu`.
- `src/core/learning.js:338` — `modelScore`: `if (!this.trained || this.sampleCount < this.config.coldStartRatings) return 0;`
- `src/core/Schedule.js:176–179` — `_modelIsTrustworthy` rejects a negative skill.
- `src/ui/components/Cabana.jsx:194–196` — the sentence the user reads.

**Probe output (wrong value).** The boundary sweep, with `coldStartRatings = 10`:

```
coldStartRatings = 10
groups=3 n=12 skill=-49                  maySpeak=false | foldTrain=8  subTrained=true subPreds=[0,0,0,0]
groups=3 n=14 skill=-34.230446521573036  maySpeak=false | foldTrain=9  subTrained=true subPreds=[0,0,0,0,0]
groups=3 n=16 skill=-2.899466826540592   maySpeak=false | foldTrain=10 subTrained=true subPreds=[0.984,0.736,0.994,0.744,1,0.753]
groups=4 n=12 skill=-27.125000000000007  maySpeak=false | foldTrain=9  subTrained=true subPreds=[0,0,0]
groups=4 n=14 skill=-0.03871744721991055 maySpeak=false | foldTrain=10 subTrained=true subPreds=[0.930,0.922,0.917,0.917]
groups=4 n=16 skill=-0.013366932940471976 maySpeak=false | foldTrain=12 …
groups=4 n=18 skill=0.03331547844933769  maySpeak=TRUE  | foldTrain=13 …
groups=6 n=12 skill=-0.5163952307013122  maySpeak=false | foldTrain=10 …
```

Read the `subPreds` column: wherever `foldTrain < 10` the sub-model is trained but
answers `0` to every question, and `skill` collapses to −49 / −34 / −27. Where
`foldTrain >= 10` the same data yields −0.04 to +0.03. The discontinuity between
`n=12` (−27) and `n=14` (−0.039) at the same 4 groups is entirely the cold-start floor,
not the data.

**Right value.** A fold sub-model must be scored as a model or not used at all — either
the fold fit ignores `coldStartRatings` (it is a measurement, not a user-facing
prediction), or a muzzled sub-model must fall back to `mu` the way an untrained one does.
Either way `n=12` should land near the −0.04…+0.03 band its own data supports, not −27.

**Anti-vacuity check.** Three independent things prove the fixture reaches the mechanism.
(a) The probe re-runs one fold by hand and prints `sub.trained = true` alongside
`sub.modelScore(held-out)` — so the `0`s are demonstrably coming from the cold-start
early return inside `modelScore`, not from an untrained model taking the `mu` branch.
(b) The same rating generator, the same group count, and only the sample count varied
produces −27 at `foldTrain=9` and −0.039 at `foldTrain=10`: the step lands exactly on the
threshold. (c) `maySpeak` flips to `true` at `groups=4, n=18`, so the gate is live and the
probe is not asserting into a constantly-false function.

**Where the case is wrong.** It predicts the failure "for every user between 12 and
roughly 20 ratings". Measured, the catastrophic band is narrower — `n = 12–14` with 3–4
groups — and its own headline fixture (14 ratings, 4 groups) gives a *marginal* −0.039,
not a catastrophic value. The claimed cause is right; the claimed range is not.

**Also confirmed — the reciprocal boundary the case names in its last sentence.**

```
B107b identical ratings: skill = null maySpeak = true _weights().preference = 0.08823529411764706
```

A user who rates everything `5` — a dataset with no signal whatsoever — gets `errMean === 0`,
`skill = null`, and **full model authority**, while the user with genuine 4/5 variance at
n=12 is measured and silenced. `src/core/learning.js:411` (`if (n === 0 || errMean === 0) return null;`).

**Probe source** (`tests/zz-hunt2-learning2.test.js`, abridged):


### 3. B105 — a rating history that is one recurring series buys full model authority

**Defect.** `_assessSkill` folds by `parentId ?? id`; 22 ratings on one recurring task are
one group, `groups.length < 3` returns `null`, and `null` passes `modelMaySpeak()`. The
gate built to stop an untested model from steering the week opens **because** the model
could not be tested.

**File:line.** `src/core/learning.js:387` (`if (groups.length < 3) return null;`),
`src/core/Schedule.js:176–179` (`!(typeof skill === 'number' && skill <= 0)`),
`src/core/Schedule.js:509` (`ratedSamples` stamps `parentId: t.id` on every synthesised
occurrence, which is what collapses the groups).

**Probe output (wrong value).**

```
samples = 22 distinct fold groups = 1
skill = null (null = "not assessed")
modelMaySpeak() = true
_weights().preference = 0.08823529411764706
_modelScore(a real sample) = 0.45464823979048175
openings.modelCanSpeak(s, "gym") = true
learning.vocab = ["gym"]
```

and, from the first probe, the weight vector with and without the model:

```
B105 weights WITH model  : {"proximity":0.294,"balance":0.206,"stability":0.088,"preference":0.088,"buffer":0.235,"energy":0.088}
B105 weights WITHOUT     : {"proximity":0.323,"balance":0.226,"stability":0.097,"preference":0,   "buffer":0.258,"energy":0.097}
```

**Right value.** `modelMaySpeak()` must be `false` and `preference` must renormalise to
`0`, as it does for a fresh schedule. The doctrine "`null` means not-assessed, treated as
passing so a small honest dataset is not punished for being small"
(`src/core/Schedule.js:157–159`) was written for the **small** case; it is being applied
to a 22-sample case that is not small, only *unsplittable*. Two different situations, one
`null`.

**Anti-vacuity check.** The ratings were written through the real door (`rateOccurrence`
on occurrences produced by `getTasksForWeek`), so they live in
`parent.occurrenceData[key].satisfaction` and reached the model only via `ratedSamples()`
— `samples = 22` proves the door worked, and `sampleCount = 22` proves `train` consumed
them. `_modelScore` returned `0.4546`, a real number, so the model is genuinely steering
placement rather than being neutralised downstream. And the side-by-side print against a
fresh `Schedule` shows `preference: 0` under correct behaviour, so the fixture would have
printed something different if the gate had held. `groups = 1` is printed directly, so
the collapse is the named mechanism.

**Honest limit on the blast radius.** The case claims all four doors narrate. Placement
steering is unconditional and proven above. The two *narration* surfaces (Cabana's
`learned` list, the wrap report's `top`) additionally filter on weight magnitude, and in
this fixture the weights are tiny (`day:tue = −0.011`, `day:thu = 0.011`), so they would
print little or nothing here. The narration harm is real but contingent on the series
carrying a strong signal; the placement harm is not contingent on anything.

### 4. B106 (divergence half only) — a diverged fit leaves the previous `skill` in place, and the gate opens on it

**Defect.** The divergence guard zeroes the weights, sets `trained = false` and returns
**before** `this.skill` is assigned, so the skill from the last good fit survives. With
`sampleCount` still at 30, `modelMaySpeak()` returns `true` for a model that does not
exist, and `_weights()` keeps the `preference` channel live at 0.088 — taking ~9% off
every other weight in favour of a channel that scores identically zero.

**File:line.** `src/core/learning.js:313–321` — the guard's `return this;` sits above
`this.skill = …` at line 332.

**Probe output (wrong value).**

```
B106b before: skill = 0.49016964210620284 maySpeak = true
B106b after DIVERGED train: skill = 0.49016964210620284 trained = false diverged = true sampleCount = 30 maySpeak = true
B106b _weights() = {"proximity":0.294,"balance":0.206,"stability":0.088,"preference":0.088,"buffer":0.235,"energy":0.088}
B106b _modelScore = 0
B106b inspect top = []
```

**Right value.** `skill` must be `null` (or the divergence must be visible to
`_modelIsTrustworthy`) so `maySpeak = false` and `preference` renormalises to `0`, as it
does for a schedule with no model at all.

**Anti-vacuity check.** The divergence really happened, and the probe proves it three
ways rather than assuming it: `diverged = true`, `trained = false`, and
`inspect() = []` (every weight zeroed by the guard). `sampleCount = 30` shows the run got
past the empty-samples early return, so it is the *divergence* branch that was taken and
not the zero-sample one. `skill` printed identically before and after (`0.4901696421…` to
the last digit), which is what "stale" means. Divergence was forced with
`learningRate: 1e9`, an option `train` already accepts — no source was touched.

**How much of it the user sees, honestly.** Less than the case claims. Two downstream
guards absorb most of it: `modelScore` refuses to score an untrained model (`_modelScore = 0`),
and `Cabana.jsx:192` tests `learning.diverged` **before** it tests `modelMaySpeak()`, so
the Cabana correctly says "the last fit did not converge". What actually leaks is (a) the
diluted weight vector in placement — a scoring channel that contributes zero to every
candidate while still holding 8.8% of the normalised budget — and (b)
`report.js:354`'s `buildInsight`, which leaves the `cold: true` branch and returns
`{ cold: false, sampleCount: 30, top: [] }`, i.e. the report presents itself as having a
model with nothing to say rather than as having no model. Real, but a second-order effect.

### 5. Not in any case — the **fifth door** on the model gate

`src/core/openings.js:45`:

```js
export function modelCanSpeak(schedule, tag) {
  const m = schedule.learning;
  if (!m || !m.trained) return false;          // ← `trained`, not `schedule.modelMaySpeak()`
```

This is the known repeat defect the gate's own docstring at `Schedule.js:162–170`
enumerates ("wired into `_weights` and `_modelScore` only, while `whatToDo`, the wrap
report's insight and the Cabana went on testing `learning.trained` directly"). Those three
were fixed; this one was never counted. **Count of `learning.trained` readers still
bypassing `modelMaySpeak()` in `src/`: exactly 1** — `openings.js:45`. Measured:

```
skill = -0.4370713320744237 | modelMaySpeak() = false | learning.trained = true | modelCanSpeak(schedule,"tag0") = true
```

So a fit **measured as worse than predicting the user's average** is silenced in
placement, the compass, the Cabana and the wrap report, and still reorders the "find
another time" openings by "what you have actually done" (`openings.js:95`).

*Anti-vacuity:* the same schedule object is asked both questions in the same statement and
they disagree; `skill` is a real measured negative from a real `train` call, not injected.

> **Already being fixed elsewhere.** Measured against `HEAD`. After this probe ran, a
> concurrent agent's uncommitted change to `src/core/openings.js` in the working tree
> replaces `if (!m || !m.trained) return false;` + the hand-copied cold-start comparison
> with `if (!m || !schedule.modelMaySpeak()) return false;`. Same defect, same door.
> Recorded here as independent confirmation from a second direction — **do not fix twice**.

### 6. B108 — a legacy occurrence with no `endAt` teaches the model a **fabricated 60 minutes** (not a zero)

**Defect confirmed, mechanism corrected.** `ratedSamples` synthesises
`endTime: od.endAt ? new Date(od.endAt) : start`, and `Task`'s constructor then converts
`end === start` into `start + DEFAULT_DURATION`. So the sample does not get a zero-minute
duration and does not land in the first bucket — it gets an **invented one-hour
duration**. For a 20-minute session that is the wrong duration column entirely.

**File:line.** `src/core/Schedule.js:488` (`endTime: od.endAt ? … : start`) meeting
`src/core/Task.js:51–53` (`end === start` → `addMinutes(start, DEFAULT_DURATION)`).

**Probe output (wrong value).** A 20-minute recurring session, one legacy occurrence and
one current one:

```
B108 samples = 2 (3 entries, one has no `at`)
   2026-06-01 start 2026-06-01T11:00:00.000Z end 2026-06-01T12:00:00.000Z duration = 60
   2026-07-01 start 2026-07-01T11:00:00.000Z end 2026-07-01T11:20:00.000Z duration = 20
B108 legacy  (no endAt) duration bucket = [ 'dur:45-90' ]
B108 current (endAt)    duration bucket = [ 'dur:15-30' ]
```

**Right value.** Both samples describe the same 20-minute session. The legacy one must be
skipped — the treatment its own sibling already gets when `at` is missing
(`Schedule.js:479`, and `samples = 2` above proves that skip fires) — or its duration
feature must be left unset. `dur:45-90` is not a neutral default; it is a positive vote in
a column the user never earned.

**Anti-vacuity check.** The two occurrences are identical in every field except `endAt`,
so the difference in the printed bucket can only come from that field. The current sample
lands in `dur:15-30`, which is what correct behaviour looks like on the same line of
output — so the probe would have printed the same bucket twice had the field been handled
honestly. `samples = 2` from three `occurrenceData` entries independently confirms that
the `at`-less entry was dropped, i.e. the two halves of the function really do disagree
about what a missing field means. The first probe additionally showed that a fixture whose
sessions are genuinely 60 minutes prints `zero-duration samples = 0` and identical
durations throughout — which is exactly why this defect has never surfaced: the pre-`endAt`
gym fixture happened to be an hour long, so the invention was invisible.

**The case's central claim is false.** `durations = [60,60,…]`, `zero-duration samples = 0`.
There is no zero, no first bucket, and no "you like very short sessions". Ranked last
because it also needs a save written before `endAt` existed — today `rateOccurrence`
stamps `at` and `endAt` together in one branch (`Schedule.js:448–449`), so no new data can
enter this state.

## NOT PRESENT

**B109 — a commitment of amount zero.** Refuted by one line of output: `previewWeek`
classifies it `state = outside`, so `layOutWeek` never builds an input for it.

```
B109 previewWeek row: state = outside remainingMin = 0 owedMin = 0 input = present
B109 layOutWeek results = []
B109 sittings on the grid = 0
B109 chooseSittings(amount=0, sMin=0) = [0] shortfall = 0     ← the engine, called directly
```

The last line confirms the engine hazard is exactly as described — a zero-minute sitting,
`endTime === startTime` — but **there is no second caller**. `generateAll` is called from
`commitmentWeek.js:139` and nowhere else in `src/`; `generateSittings` is called from
`generateAll` and nowhere else. Both of the case's named user actions ("Lay out this week",
and the multi-commitment path) are the same function, behind the same filter, and it is a
double guard (`state === 'owes'` **and** `remainingMin > 0`). Latent, not live.

**B111 — mark done then unmark, on a blocked week.** The case is self-refuting in its own
scenario: the week it specifies has nothing to lose.

```
B111 (1) sittings = 0 shortfall = 240
B111 (1) row: state = owes placedMin = 0 remainingMin = 240 owedMin = 240
B111 (2) marked: removed = 0 kept = 0
B111 (2) row: state = done placedMin = 0 remainingMin = 0 settled = true
B111 (3) after unmark: state = owes placedMin = 0 remainingMin = 240 sittings on grid = 0
```

Step (1) is exactly the expected `0/240m short 240m`; step (2) overrides the arithmetic
and still reports `placedMin = 0` honestly; step (3) restores step (1) **exactly**, because
`removed = 0`. The round trip on this week is lossless.

The lossy round trip does exist on an *unblocked* week —

```
B111b before: sittings = 2 placedMin = 240 remainingMin = 0
B111b after mark+unmark: removed = 2 sittings = 0 placedMin = 0 remainingMin = 240 state = owes
```

— but that is the documented decision, spelled out in `Schedule.js:632–636`: "un-marking
says 'I was wrong, I am not finished', not 'put my old plan back'. Lay it out again to get
blocks, exactly as D-14's remove leaves you." A deliberate, written-down product choice is
not a defect; if it is to be revisited it is a product question, not a bug.

**B111's third seam — "three different weeks depending on which section is asking" — is
also refuted.** `sittingsFor` selects on `dateKey` strings (`Schedule.js:588–593`), and the
report's routine section selects on `[ws.getTime(), addDays(ws, 7).getTime())`
(`report.js:780–781`). `addDays` is `d.setDate(d.getDate() + days)` (`time.js`), which is
calendar-arithmetic, so `addDays(ws, 7)` is the next Monday's local midnight even across
the 1 November DST change. The two ranges are the same seven days. A Sunday 23:30 sitting
is in the same week for both readers.

**B106's zero-samples half.** Refuted by one line: `sampleCount` is assigned at
`learning.js:205`, *above* the empty-samples early return, so an empty retrain zeroes it
and the cold-start half of the gate closes the door the stale skill left open.

```
B106a after real train:  skill = 0.4901696421 trained = true  sampleCount = 30 maySpeak = true
B106a after EMPTY train: skill = 0.4901696421 trained = false sampleCount = 0  maySpeak = false
```

The skill *is* stale (identical to 10 digits), but nothing reads it in that state. Only
the divergence half, above, is live.

## STALE

Nothing in B105–B111 names `placedByUser` or `moveCount`, so none of these cases is stale
against `MODEL_LAYOUT_VERSION = 6` (c0766ad dropped `placedByUser`; v5 dropped
`moveCount`). Every symbol the seven cases name — `_assessSkill`, `modelMaySpeak`,
`ratedSamples`, `chooseSittings`, `effectiveMinSitting`, `markCommitmentWeekDone`,
`DURATION_EDGES` — exists at the line the case implies.

Two *sub-claims* are stale rather than wrong:

- **B107** describes the gate silencing "the entire population between 12 and roughly 20
  ratings". Measured, the catastrophic band is 12–14 and the marginal band runs to ~16.
